# TDDと検証

振る舞いを追加・変更するコードは、アプリ・スクリプト・hookを問わずRed → Green → Refactorで進める。

1. 受け入れ条件を、外から確認できる振る舞いに落とす。
2. テストを先に書いて実行し、意図した振る舞いが未実装であるために失敗することを確認する。環境不備・構文エラーで落ちただけの結果をRedとしない。
3. テストを通す最小の実装を行う。
4. Greenを保ちながら構造を整理し、影響する既存テストも確認する。

不具合修正では、修正前に再現する回帰テストを先に置く。実装後にテストを足した場合は、TDDを実施したと報告せず、順序と理由を明記する。

## テストの選び方

- 実装の内部手順を写すだけのテストではなく、要件を満たさない実装なら失敗するテストを書く。
- 入力の境界、欠損、失敗、データ保全を変更に応じて確認する。
- ネットワークや外部書き込みは通常の自動テストで実行しない。必要な統合確認は隔離した対象で行い、範囲を明記する。
- 純粋な文書・リンク変更はリンクやコマンドの動作を確認する。文面の一字一句を固定するテストは書かない。
- Figmaや見た目の変更は対象状態・操作・アクセシビリティを確認する。UIの振る舞いをコードにする段階ではテストを先に書く。

## 記録と完了

Redの対象と失敗理由、Greenの結果、回帰確認を成果物に残す。未実施・実行不能・不合格を合格と混同しない。必要な確認が通り、新たな変更・失敗・懸念がなければ、同じテストを理由なく繰り返さない。
