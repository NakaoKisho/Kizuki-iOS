# レビューの固定チェックリスト

担当・段階・指摘の扱いは[判定と受入](policy.md)に従う。各観点は設計時に扱いが定義されているか、実装時にその定義どおりかを確認する。機能に該当しない項目は理由を添えて「該当なし」とする。

| ID | 観点 | Kizukiで確認すること |
| --- | --- | --- |
| V01 | 目的 | 受け入れ条件を満たしても目的から外れないか。少ない操作で記録・振り返り・受診時の提示や読み上げができるか。読みやすさ・操作性・アクセシビリティを含む |
| V02 | 前提の事実 | 既存コード、完全版Xcodeと選択中のDeveloper Directory、API、ライブラリ、Figmaや設定の実物と前提が合うか。未導入・未実装を利用可能と誤記していないか |
| V03 | 実行経路 | 対象OS・CLI・ビルド・画面遷移・保存・出力の経路がつながるか。ローカルだけのファイルや特定のPCのパスに依存しないか |
| V04 | 入力の境界 | 空・欠損・上限・不正入力・未記録と症状なしを区別できるか。尺度の範囲と単位が明確か |
| V05 | 期間 | 記録日時・タイムゾーン・日付境界・集計期間が一貫するか。記録途中の当日を含む場合にその意味が伝わるか |
| V06 | 失敗の扱い | 入力・保存・読込・出力・コマンドの失敗が利用者や作業者に伝わるか。失敗を症状なし・空データ・成功に置き換えないか |
| V07 | データの保全 | 編集・削除・移行・中断で既存記録や対象外データが壊れないか。同じ入力と条件で集計値が一致するか |
| V08 | 値の中身・プライバシー | ログ・Issue・Figma・PR・リポジトリに実在の体調情報や秘密が出ないか。レポートへの情報掲載・外部共有が利用者の意図した範囲か |
| V09 | 検証の強さ | 受け入れ条件・不変条件に検証が対応するか。条件を満たさない実装で失敗する確認になっているか。未実施・実行不能を明示しているか |
| V10 | 仕様との整合 | Issue、詳細設計、Figma、実装、レポートの値と表現が一致するか。要約に記録のない事実・診断・原因の断定が混入していないか |
| V11 | スコープ | 目的に対して変更が過不足なく、対象外とした内容が目的達成を妨げないか。無関係な変更・ファイルを含まないか |
| V12 | リポジトリのルール | AGENTSと該当する詳細ルール、worktree・ブランチ・PRの向き、共有標準の管理境界を守るか |
| V13 | 既存の挙動 | 他の画面・利用箇所・既存データに影響しないか。必要な回帰確認が、対象の版に対して行われているか |
| V14 | 保守性 | 責務・定義の重複、文書の肥大化、未使用の処理がないか。文書の分割・リンクが適切か。 |

## 段階ごとの証拠

- 設計では関連Issue、Figma、調査した実物を根拠にする。受け入れ条件と検証方法の対応に抜けがないか確認する。
- 検証記録の確認では対象の版、実行環境、コマンドまたは操作、結果を確認する。対象が異なる記録を最終版の検証として扱わない。
- 実装ではファイル・行・画面などの具体的な箇所を示す。生成物がある場合は実物も見る。
- 受入では必要な観点と段階がそろい、指摘が解消したか、理由付きで対象外になったかを確認する。
