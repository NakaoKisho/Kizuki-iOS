# レビューの判定と受入

## リスクと段階

親エージェントはIssueまたはPRにリスクと理由を記載する。変更範囲が広がれば再判定し、必要な段階を追加する。出力の存在・形式・対象版は共通CLIで検査し、リスクや内容の妥当性は親が判断する。

| リスク | 対象 | 必要な段階 |
| --- | --- | --- |
| low | 意味を変えない文言・リンク修正、挙動を変えない整理 | 親の検証 → 独立reviewer 1名による全観点確認 → 親の受入 |
| medium | 機能・UI・集計仕様の変更、開発やレビューの運用ルールの変更 | 設計レビュー → 親の検証 → 検証記録の独立確認 → 実装レビュー → 親の受入 |
| high | 実データの保存・削除・移行・外部共有、秘密情報・権限、署名・配布・CIの権限経路 | mediumの全段階に加え、影響する失敗・情報露出・復旧経路の検証 |

medium・highの設計レビューと実装レビューは複数の独立担当で行い、チェックリストの全適用観点を網羅する。初期ルールの文書化はmediumとし、CIや配布経路そのものを変更する場合はhighとする。重大指摘が出たらリスクを1段上げ、必要な検証を追加する（highは維持）。

| 段階 | 対象と確認内容 |
| --- | --- |
| 設計 | Issueの目的・受け入れ条件、設計案。不変条件ごとに検証方法を対応付ける。未実装自体は不備としない |
| 検証 | 親または実行担当が、変更に必要なテスト・ビルド・実機確認を行う。文書はリンクと記載コマンドの動作を確認する |
| 検証記録の独立確認 | 作者以外の担当がV09・V10・V13で検証対象、方法、結果、検証不足を確認する。テスト・品質の専門性を持つ担当を選び、実装作者とは分離する |
| 実装 | 固定観点で実際の差分と仕様・Figmaとの一致を確認する |
| 成果物 | 生成したレポート・画像・データ等を追加する場合、リスクに関係なく元データとの一致・対象範囲・情報露出を確認する。通常の手書きMarkdownのみなら対象外 |
| 受入 | 親が必要な担当の報告、検証記録、受け入れ条件、最終差分を突き合わせる |

コマンドの動作確認は、一時リポジトリなど外部を変更しない環境で行ってよい。push・PR作成などは、許可された実作業の結果を証拠にできる。文面の完全一致を要求するテストは作らない。

## 指摘の記録と再確認

- 指摘には一意のID、観点ID、重大度、対象箇所、具体例、影響、修正案または確認事項を付ける。
- 「重大」は目的の不達、データ消失、情報露出、主要動作の破綻。「通常」は修正が必要な問題。「提案」は任意の改善とする。
- 各観点を「問題なし」「指摘あり」「該当なし」で答え、根拠や対象外の理由を残す。検証結果は「pass」「failed」「verification gap」で区別する。
- 親は指摘を「修正」「根拠を示して不採用」「未解決」に整理する。意見の相違は多数決で決めない。
- 再レビューでは前回の指摘を同じIDで追跡し、「解消」「未解消」「対象外」と根拠を示す。未解消は今回の指摘にも再掲する。
- 再レビューの対象は指摘の解消と変更の影響範囲とする。新しい問題や変更がなければ、レビューを最初から繰り返さない。
- 重大・通常の未解決指摘が0になり、必要な検証が確認できたら受入へ進む。任意の提案は対応するか、追跡するIssueへ分離する。
- 必須検証のverification gapを合格にしない。サブエージェントを利用できない場合は独立レビュー未実施と記録し、自分の再確認で置き換えない。
