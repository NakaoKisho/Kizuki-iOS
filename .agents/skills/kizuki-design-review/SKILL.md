# 設計レビュー

[共通レビュー規約](../kizuki-review/SKILL.md) を読み、リスク・担当・出力を決める。設計を作る段階から適用する製品確認項目を使い、独立レビューに備える。

1. 関連Issueの目的・受け入れ条件、設計案、Figmaの対象、既存コードや公式資料を揃える。未決定事項を採用済みとしない。
2. 固定観点ごとに、設計で扱いが定義されているか確認する。不変条件と検証方法を対応付け、失敗時や対象外にした範囲も確認する。未実装であること自体を不備としない。
3. iOSの技術判断は担当の定義に従い公式資料と照合する。UI・Figmaは必要な表示状態と操作の根拠を確認する。
4. 指摘と未確定事項を報告する。親は指摘対応と必要な再レビューを終え、checkと内容の受入を確認してから実装へ進む。

設計変更で既存判断が変わる場合は [kizuki-issue](../kizuki-issue/SKILL.md) で判断を記録する。レビュー依頼だけを根拠にマージ・配布は行わない。
