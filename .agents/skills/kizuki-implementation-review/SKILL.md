# 実装と検証記録のレビュー

[共通レビュー規約](../kizuki-review/SKILL.md) を読み、リスクに必要な段階と担当を確認する。medium・highでは設計レビューの受入結果も確認する。

1. 対象版と差分、Issueの受け入れ条件、設計・Figma、実施した検証記録を揃える。
2. 作者と別の品質担当が、V09・V10・V13で対象版、実行環境、コマンドや操作、結果、検証不足を確認する。[TDD方針](../../../.codex/rules/testing/AGENTS.md) に照らし、実際のRed・Green・回帰確認を区別する。
3. 全適用観点について実際の差分を確認し、ファイル・行・画面を根拠にする。UIはFigmaの対象状態と比較し、iOSコードは担当定義に従い公式資料を確認する。
4. 生成したレポート・画像・データ等があれば実物と元データ、対象範囲、情報露出を確認する。未確認の実機・Figma・出力を成功としない。
5. 前回指摘は同じIDで追跡し、解消と変更の影響を再確認する。親は必須検証と未解消指摘を確認し、checkと内容の受入後に結果を報告する。

lowの文言・リンク整理は共通規約の省略可能な段階に従う。通常の手書きMarkdownのみなら生成成果物の検査は対象外とする。
